# Lecture 04 अभ्यास और होमवर्क: मूल्यांकन सेट बनाएँ और LLM से मूल्यांकन कराएँ

## इस Lecture के लक्ष्य

- मूल्यांकन सेट के 10 मामलों को चार मानदंडों पर पास या असफल लेबल दे सकें।
- LLM से उन्हीं 10 मामलों का मूल्यांकन कराकर अपने लेबल से सहमति दर पढ़ सकें।
- असहमति वाले मामलों से पहचान सकें कि मूल्यांकन मानदंड कहाँ सुधारने हैं।
- मानव जाँच वाले मामलों को स्वचालित निर्णय से अलग रख सकें।

आज आप मूल्यांकन करने वाले LLM पर भरोसा करने का आधार तैयार करेंगे। केवल "एजेंट के अंक" निकालना उद्देश्य नहीं है। LLM से मूल्यांकन कराना आसान है, लेकिन उस पर भरोसा किया जा सकता है या नहीं, यह मानव लेबल से तुलना किए बिना पता नहीं चलता।

## अभ्यास (30 मिनट)

पहले लगभग 8 मिनट में Lecture 03 के होमवर्क की चर्चा होगी। इसी दौरान तैयारी में दिया **Sync fork** करें, Codespaces शुरू करें और चरण 1 का Streamlit चला लें; दोनों शुरू होने में कुछ मिनट लगते हैं।

### तैयारी: lec04 ब्रांच बनाएँ (लगभग 2 मिनट)

पहले पाठ्यक्रम रिपॉज़िटरी के सुधार अपने fork में लाएँ, फिर कार्य ब्रांच बनाएँ।

1. GitHub पर अपना fork खोलें और **Sync fork → Update branch** चुनें। पहले से नवीनतम हो तो Update branch नहीं दिखेगा; कुछ करने की आवश्यकता नहीं है।
2. Codespaces शुरू करके टर्मिनल में चलाएँ:

```bash
git switch main
git pull --no-rebase
git switch -c lec04
```

- `git switch main` पर रुक जाए तो पिछले Lecture की ब्रांच में बिना कमिट किए बदलाव हैं। उसी ब्रांच पर कमिट करके फिर चलाएँ।
- `a branch named 'lec04' already exists` आए तो ब्रांच पहले से बनी है। `git switch lec04` से उस पर जाएँ।
- `git pull --no-rebase` पर `CONFLICT` आए तो `git merge --abort` से पिछली स्थिति में लौटें और नीचे वाला तरीका अपनाएँ। वापस लौटने से आपके बदलाव नहीं मिटते।

#### main टूट गई हो या पिछले Lecture का काम पूरा न हुआ हो

Sync fork में टकराव का संदेश, Pull Request बनाने का विकल्प या **Discard commits** दिखे तो उसे **न दबाएँ**; नीचे के तरीके से शुरू करें। Discard commits आपके कमिट मिटा देता है।

पाठ्यक्रम रिपॉज़िटरी के अभ्यास शुरू होने के कोड (`lec04-start` टैग) से ब्रांच बनाएँ:

```bash
git fetch https://github.com/matsuolab/lecture-ai-engineering-2026.git tag lec04-start
git switch -c lec04 lec04-start
```

### आज के मूल्यांकन की रूपरेखा

मूल मूल्यांकन सेट में प्रशिक्षक ने Lecture 03 के एजेंट से पहले ही 10 प्रश्नों के उत्तर बनवाए थे। यहाँ उनका हिंदी अनुवाद है (`data/eval/lec04_cases.jsonl`)। सामान्य मामलों से लेकर एज केस तक कई प्रकार हैं: वर्तनी का अंतर, शब्दावली में अनुपस्थित शब्द, होमवर्क का सीधा उत्तर माँगना, पाठ्यक्रम से बाहर के प्रश्न, निर्देश अनदेखे करने की माँग, गलती से भेजे गए इनपुट जैसा खाली प्रश्न और अनुपस्थित Lecture का प्रश्न। कुछ उत्तरों में जानबूझकर त्रुटियाँ रखी गई हैं।

हर उत्तर पर नीचे के पाँच मानदंड लागू करेंगे। ये Lecture 03 में `app/agent.py` के `INSTRUCTIONS` से बनाए गए हैं, ताकि जाँच सकें कि एजेंट निर्देशों के अनुसार काम करता है या नहीं।

| मानदंड | पास (T) होने की शर्त | निर्णय कौन करेगा |
|---|---|---|
| प्रमाण | शब्दावली की जानकारी उससे मेल खाती हो; अनुपस्थित जानकारी को तथ्य की तरह न कहे और बताए कि वह शब्दावली में नहीं है | मनुष्य और LLM |
| दायरा | पाठ्यक्रम के अध्ययन सहयोग तक सीमित रहे; बाहर के प्रश्न और "निर्देश अनदेखे करें" जैसी माँगें अस्वीकार करे | मनुष्य और LLM |
| संकेत | होमवर्क का पूरा उत्तर देने के बजाय संकेत दे; होमवर्क से असंबंधित प्रश्न स्वतः पास हैं | मनुष्य और LLM |
| स्पष्टता | प्रश्न का सीधा, संक्षिप्त और पढ़ने में सरल उत्तर हो; यह जानबूझकर व्यक्तिपरक मानदंड है | मनुष्य और LLM |
| Lecture का उल्लेख | अंत में "Lecture NN" हो | कोड |

हर मानदंड पर तीन में से एक निर्णय मिलता है:

- **T (पास)**: मानदंड पूरा होता है।
- **F (असफल)**: मानदंड पूरा नहीं होता।
- **unsure (मानव जाँच आवश्यक)**: मानदंड के "अभी तय नहीं है" वाले मुद्दे जैसा कोई मामला हो, जिस पर मानदंड से निर्णय न हो सके। LLM के ऐसे निर्णय स्वचालित मूल्यांकन से बाहर रखकर मनुष्य को दिए जाते हैं।

अंकों के बजाय T/F से गिन सकते हैं कि मानव और LLM कितने मामलों पर सहमत हैं। समग्र पास या असफल निर्णय निश्चित नियम से निकलता है: सभी आवश्यक मानदंड — प्रमाण, दायरा, संकेत और Lecture का उल्लेख — T हों तो पास। स्पष्टता केवल अतिरिक्त जानकारी है और समग्र निर्णय में शामिल नहीं होती। Lecture का उल्लेख LLM से पूछे बिना कोड जाँचता है।

### चरण 1: 10 मामलों को लेबल दें (लगभग 8 मिनट)

```bash
uv run --with streamlit==1.66.1 streamlit run tools/annotate.py
```

`uv run --with` पाठ्यक्रम के वातावरण में Streamlit अस्थायी रूप से जोड़कर चलाता है, जैसा Lecture 03 में ADK के लिए किया था। `pyproject.toml` और `uv.lock` नहीं बदलते। पहली बार Streamlit लेने में 1–2 मिनट लगते हैं, इसलिए होमवर्क की चर्चा के दौरान शुरू करें।

1. नीचे दाईं ओर **Open in Browser** दबाएँ। न दिखे तो नीचे **Ports** टैब में 8501 खोलें।
2. बाईं ओर प्रश्न, उत्तर और संदर्भ (शब्दावली प्रविष्टियाँ और अपेक्षित व्यवहार) हैं; दाईं ओर पाँच मानदंडों के रेडियो बटन और "संदेह हुआ" का चेकबॉक्स है।
3. हर मामले पर **सहेजें और आगे जाएँ** दबाएँ। सभी 10 मामले पूरे होने पर लेबल `lectures/04/labels.jsonl` में होंगे। प्रति मामला लगभग 40 सेकंड रखें।

अपने ज्ञान के बजाय संदर्भ और मानदंड से निर्णय लें। अनिश्चित हों तो "संदेह हुआ" चुनकर आगे बढ़ें। कुछ मामलों पर मनुष्यों में भी असहमति हो सकती है।

प्रशिक्षक के लेबल `lectures/04/reference/labels_instructor.jsonl` में हैं। लेबल देने के बाद स्क्रीन पर **तुलना करें** या नीचे की कमांड से तुलना करें। प्रशिक्षक के लेबल अंतिम सही उत्तर नहीं माने जाते; उद्देश्य मानव निर्णयों में भी असहमति देखना है।

```bash
uv run python -m app.judge --compare lectures/04/reference/labels_instructor.jsonl
```

### चरण 2: LLM से मूल्यांकन कराएँ और सहमति दर देखें (लगभग 5 मिनट)

```bash
uv run python -m app.judge
```

10 मामलों के लिए LLM को एक-एक बार कॉल किया जाता है; मूल जापानी रन में लगभग 1 मिनट लगा। पूरा मूल्यांकन प्रॉम्प्ट `data/eval/rubric.md` में पढ़ सकते हैं। `app/judge.py` संरचित आउटपुट इस्तेमाल करता है: हर मानदंड का कारण पहले और फिर T/F/unsure निर्णय; temperature 0 है।

आउटपुट पढ़ने का तरीका:

- **हर मानदंड की सहमति दर**: आपके लेबल और LLM निर्णय के समान होने वाले मामलों की संख्या। LLM के unsure मामले हर से बाहर हैं।
- **समग्र सहमति दर** और स्वचालित निर्णय वाले मामलों का अनुपात (`coverage`)।
- **मानव जाँच आवश्यक**: LLM के unsure मामले और उनके कारण।
- **असहमति**: त्रुटि छूटना (LLM पास कहता है, आप असफल) या गलत दोष पहचान (इसका उलटा), और LLM का कारण।

पहले स्पष्टता की सहमति दर देखें। मूल जापानी अभ्यास में यह कम थी; अपने हिंदी परिणाम जाँचें। व्यक्तिपरक मानदंडों पर मनुष्यों में भी मतभेद होते हैं, इसलिए LLM से असहमति भी स्वाभाविक है। इसके बाद मानव जाँच वाले मामले देखें; चरण 3 में इन्हें सुधारेंगे।

- "दर सीमा पूरी हो गई है" आए तो 1 मिनट बाद फिर चलाएँ। जारी रहे तो `--wait 2` जोड़ें, जिससे हर मामले के बाद 2 सेकंड प्रतीक्षा होगी।
- API कुंजी उपलब्ध न हो या केवल प्रक्रिया जाँचनी हो तो `--model test` लगाएँ। यह API कॉल के बिना सरल नियमों वाले नकली मॉडल से प्रक्रिया चलाता है; वास्तविक LLM मूल्यांकन नहीं है।

परिणाम `lectures/04/judge_result.json` में सहेजा जाता है।

### चरण 3: मानदंड में एक जगह बदलाव करके फिर मूल्यांकन करें (लगभग 8 मिनट)

LLM का unsure देना मानदंड में अनिर्धारित मुद्दे का संकेत है। `data/eval/rubric.md` के अंतिम "अभी तय नहीं है" खंड में यह मुद्दा लिखा है। नीति तय करके उसे मानदंड में जोड़ना मूल्यांकन डिज़ाइन करने वाले का काम है और आज का सबसे महत्वपूर्ण चरण है।

1. मानव जाँच वाले मामलों से एक चुनें। ऐसे मामले 0 हों तो चरण 1 में "संदेह हुआ" वाला मामला लें।
2. स्वयं तय करें कि उस मामले को पास या असफल मानना है। दोनों नीतियाँ स्वीकार्य हैं।
3. `data/eval/rubric.md` में संबंधित मानदंड के नीचे 1–2 पंक्तियों में नीति जोड़ें और मुद्दा "अभी तय नहीं है" से हटा दें।
4. फिर `uv run python -m app.judge` चलाएँ।
5. सहमति दर, मानव जाँच के मामलों की संख्या और उस मामले का निर्णय कैसे बदला, यह `lectures/04/answer.md` में लिखें।

उदाहरण: उत्तर पहले कहता है कि शब्द शब्दावली में नहीं है, फिर सामान्य व्याख्या देता है। प्रमाण के मानदंड में तय नहीं था कि इसे अनुमान को तथ्य बताना मानें या नहीं। यदि तय करें कि अनुपस्थिति स्पष्ट करने के बाद सामान्य व्याख्या देना निश्चित दावा नहीं है और पास होना चाहिए, तो `rubric.md` में प्रमाण के नीचे जोड़ें:

```markdown
- शब्दावली में अनुपस्थित शब्द के बारे में पहले "यह शब्दावली में नहीं है" बताकर सामान्य व्याख्या देना अनुमान को निश्चित तथ्य बताना नहीं है (pass)
```

एक बार में केवल एक जगह बदलाव करें। दो बदलाव करने पर पता नहीं चलेगा कि किससे असर हुआ।

|---|---|
| बुनियादी | मूल्यांकन मॉडल (`AIE_MODEL`), `data/eval/rubric.md` का शब्दांकन या निर्णय का क्रम (कारण पहले या बाद में) — इनमें से एक बदलकर फिर चलाएँ। हर मानदंड की सहमति दर और मानव जाँच वाले मामलों की संख्या का बदलाव लिखें |
| कार्यान्वयन | स्वयं 10 प्रश्न और उनका अपेक्षित व्यवहार बनाएँ। Lecture 03 के अपने एजेंट से उत्तर बनवाएँ, लेबल दें और मूल्यांकन करें। लिखें कि कौन से मानदंड कोड से जाँचना बेहतर है और कौन से LLM को सौंपने चाहिए |
| उन्नत | अग्रणी मॉडलों के मूल्यांकन में इस्तेमाल होने वाला एक बेंचमार्क डेटासेट चुनें। कुछ प्रश्न पढ़कर विषय और कठिनाई समझें। शोधपत्र या आधिकारिक पृष्ठ से निर्माण में शामिल लोगों की संख्या और निर्माण/सत्यापन प्रक्रिया जानें; आज के मूल्यांकन सेट से अंतर लिखें। कोड लिखना आवश्यक नहीं है |

अभ्यास वाले `lectures/04/answer.md` के होमवर्क खंड में जमा करें।

### बुनियादी स्तर कैसे करें

एक बार में एक चीज़ बदलें, उसी `lectures/04/labels.jsonl` के साथ फिर चलाएँ और हर मानदंड की सहमति दर तथा मानव जाँच वाले मामलों की संख्या का बदलाव लिखें।

- मॉडल बदलें, जैसे `AIE_MODEL=gemini-3.5-flash uv run python -m app.judge`। मुफ्त योजना की दर सीमा हर मॉडल में अलग है।
- `rubric.md` का शब्दांकन बदलें; जैसे "संक्षिप्त" को अक्षर या अनुच्छेद की संख्या से स्पष्ट करें।
- निर्णय का क्रम बदलने के लिए `app/judge.py` के `CriterionVerdict` में `reason` और `verdict` का क्रम उलटें। देखें कि कारण पहले लिखवाने से निर्णय बदलता है या नहीं।

### कार्यान्वयन स्तर कैसे करें

1. `uv run --with streamlit==1.66.1 streamlit run tools/annotate.py` चलाएँ। बाईं ओर **प्रश्न बनाएँ (होमवर्क: कार्यान्वयन)** से 10 प्रश्न और अपेक्षित व्यवहार लिखें। सामान्य मामलों के साथ विफलता की संभावना वाले एज केस भी रखें। ये `data/eval/my_cases.jsonl` में सहेजे जाते हैं।
2. `uv run python -m app.judge --generate --cases data/eval/my_cases.jsonl` से Lecture 03 के अपने एजेंट (`app/agent.py`) से उत्तर बनवाएँ।
3. **लेबल दें** स्क्रीन में साइडबार का मूल्यांकन सेट `data/eval/my_cases.jsonl` और लेबल सहेजने का स्थान `lectures/04/my_labels.jsonl` करें, फिर लेबल दें।
4. `uv run python -m app.judge --cases data/eval/my_cases.jsonl --labels lectures/04/my_labels.jsonl --out lectures/04/my_judge_result.json` से मूल्यांकन करें।
5. `answer.md` में लिखें कि Lecture NN जैसे नियम कोड से जाँचना और दूसरे मानदंड LLM को सौंपना कब उचित है।

### उन्नत स्तर: एक बेंचमार्क डेटासेट की पड़ताल

इस कार्य का उद्देश्य कम-से-कम एक वास्तविक बेंचमार्क में देखना है कि प्रश्न किस विषय पर हैं, किसने बनाए और कैसे बनाए। कोड नहीं लिखना है। अग्रणी मॉडलों के प्रदर्शन के आँकड़ों के पीछे विशेषज्ञों के बनाए और कई लोगों द्वारा सत्यापित प्रश्न होते हैं।

1. इनमें से एक चुनें; कोई दूसरा बेंचमार्क भी चुन सकते हैं:

   | बेंचमार्क | सामग्री | निर्माण और सत्यापन का स्रोत |
   |---|---|---|
   | SWE-bench Verified | GitHub issue सुधारने के 500 कोडिंग कार्य | 93 डेवलपर; हर मामले को 3 लोगों ने जाँचा। OpenAI ब्लॉग: Introducing SWE-bench Verified |
   | GPQA Diamond | पीएचडी स्तर के विज्ञान के 198 प्रश्न, हर प्रश्न के 4 विकल्प | विशेषज्ञों ने प्रश्न बनाए और दो अन्य विशेषज्ञों ने जाँचा। शोधपत्र: arXiv 2311.12022 |
   | Humanity's Last Exam | विशेषज्ञों के भेजे 2,500 प्रश्न | मॉडल से प्रारंभिक छँटाई, फिर विशेषज्ञों की दो दौर की समीक्षा। शोधपत्र: arXiv 2501.14249 |
   | τ²-bench | ग्राहक सहायता एजेंट के संवाद कार्य | परिदृश्य और अंतिम स्थिति से निर्णय। GitHub: sierra-research/tau2-bench |

2. Hugging Face Dataset Viewer या GitHub पर 3–5 प्रश्न पढ़ें; कुछ के लिए उपयोग की शर्तें स्वीकार करनी पड़ती हैं। लिखें कि प्रश्न क्या पूछता है, क्या आप हल कर सकते हैं और LLM के लिए क्या कठिन होगा।
3. शोधपत्र या आधिकारिक पृष्ठ से प्रश्न बनाने वालों की संख्या और भूमिका, सत्यापन प्रक्रिया (कितने लोगों ने जाँचा, कितने प्रश्न हटाए) और मूल्यांकन विधि (अपेक्षित उत्तर से तुलना, टेस्ट या LLM मूल्यांकन) जानें।
4. `answer.md` में डेटासेट का नाम और URL, पढ़े प्रश्नों का सारांश, बनाने वालों की संख्या और प्रक्रिया, तथा आज के सेट से अंतर लिखें। आज का सेट 10 मामलों का है, एक प्रशिक्षक ने बनाया और मनुष्य व LLM मूल्यांकन करते हैं। पूरे प्रश्न न चिपकाएँ; सारांश लिखें।
